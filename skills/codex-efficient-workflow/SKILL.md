# Codex Efficient Workflow

Version: 0.1.0 · Authored: 2026-10-08T05:17:59Z · Runtime documentation checked: 2026-10-08T05:17:59Z.
These are provenance timestamps, not proof that a model is still available. Runtime state has separate check, change, and evaluation timestamps.

Reduce total work needed for a verified result. A cheaper model that needs more retries is not automatically more economical. Respect the user's task, language, model choices, and existing project instructions.

## Start cheaply

1. Find the actual skill directory from the supplied skill path. Run `python3 <skill>/scripts/workflow.py status --project <project>`; on first use run `init` to create project-local defaults. Never assume the current directory is the project root. For a projectless task, use its working directory.
2. Read the resulting `.codex-efficient-workflow/config.json`. Resolve live user instructions over persisted settings. A user model choice is pinned unless they explicitly allow automatic upgrades. For setup/customization, read [configuration.md](references/configuration.md).
3. Follow status's `refresh_due` once per invocation. Read [model-refresh.md](references/model-refresh.md) only if due or explicitly requested. A skill runs when invoked; it is not a background monitor. A failed/offline check has a retry timestamp, not a successful-check timestamp.
4. Inspect the currently exposed delegation tool and allowed model/effort values. Use explicit model and effort with a fresh, minimal-context child when supported. Otherwise use discovered `cew_*` custom agents generated by `generate`, only if this runtime can actually select them. Do not assume a TOML file has been loaded in the current session. Do not use unsupported spawn parameters or silently inherit an expensive model. If delegation/config loading is unavailable, complete manageable work in the parent and disclose the fallback.

## Choose the smallest sufficient workflow

- Simple, clear, low-impact work: do it directly; do not create a planner, reviewer, or benchmark. The parent model is unchanged by this skill.
- Clear bounded implementation: dispatch one executor with explicit acceptance checks. Let the parent review its evidence.
- Ambiguous or architecture-heavy work: use the configured planner for a compact plan, then an executor. If the parent already has the required plan and capability, reuse it; do not pay for duplicate planning.
- Integration/debugging/judgment: use `executor_complex` directly rather than repeatedly trying the light executor. High consequence or subtle cross-component work merits a targeted reviewer, not mandatory review for every edit.
- Concurrency is allowed only for independent tasks with disjoint write scopes. Enforce `max_parallel`; same-file changes are sequential. Child agents must not spawn their own agents.

The default limits are two concurrent children, six total dispatches per task, one repair on the same model, and one escalation to `executor_complex`. Count resumed child turns as dispatches too. These are orchestration limits, not hard token or billing caps. Track actual usage only if the runtime exposes it; otherwise record unknown. Before a limit is exhausted, consolidate work in the parent if reasonable, or surface the unresolved blocker. Never claim incomplete work passed to satisfy a budget.

## Handoff and quality

Send only: objective, exact scope, necessary context/file references, constraints, acceptance checks, and required return format. Default target: `packet_target_chars` characters; truncate background, never essential requirements. Do not fork the entire conversation solely for convenience.

Planner returns a short task list with dependencies, file scopes, acceptance checks, and uncertainty. Executor returns `done|blocked|needs_review`, changed artifacts, check commands/results, and remaining concerns. A report of completion is not verification.

Use task-appropriate external evidence: tests for behavior changes; rendering for layout work; sources for factual work; a diff or actual result for small edits. Do not add tests that mirror implementation. Run required checks once; repeat only after changes, failure, or a material gap. Do not weaken checks, alter acceptance criteria, or delete failures to reduce usage.

On a failed check: send the exact failure and relevant context back once. Escalate only on demonstrated capability/judgment trouble, not credentials, permissions, unavailable services, or an invalid request. Availability errors get one configured alternate if available. Avoid repeated calls to a broken provider. Stop at configured limits and return concrete progress and the blocker.

## Model evolution

On a due check, verify official releases and account/runtime availability. Compare vendor-confirmed generation within the same configured provider/family; do not parse a model name as proof of a major release. `auto_major` roles may migrate only after a paired quality/usage gate; pinned roles remain fixed. Apply with `refresh --apply`, record an audit/back-up, and regenerate owned agent files. Unverified candidates remain pending and the working configuration stays usable. See [model-refresh.md](references/model-refresh.md).

Do not change the main chat's model, provider credentials, global Codex defaults, or unrelated agents. This skill authorizes scoped delegation when used on a suitable task; it does not authorize external actions beyond the user's request.

## User-facing result

Lead with the outcome and verification. Include the chosen role/model only when useful, plus any fallback, model update, or unresolved issue. Report measured savings only against a comparable baseline; subscription quota and API dollars are different metrics. Keep local receipts concise and omit secrets or full private prompts.

For delegated work, save a compact receipt with `record-run --project <project> --receipt <receipt.json>` using `<skill>/assets/examples/run-receipt.example.json`. Record actual model identity only when observed; unknown usage is null. Direct trivial tasks need no receipt. Timestamp receipts locally; never push them to an open-source repository.
